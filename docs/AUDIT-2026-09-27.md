# SDK design audit - 2026-09-27 (against 1.8.1, master 508f4d5)

Why this audit: in 71 commits the SDK has been patched for the same kinds of
bug again and again. Money units were mixed up four times (1.5.0, 1.5.1 and two
adapter fixes). Idempotency was fixed three times, refunds three times, fixes
were copied back from consumer forks twice, and time zones once (1.8.1). Each
consumer also carries its own workarounds. A pattern that repeats is a
design gap in the SDK, not a series of consumer mistakes. This audit
names those gaps so they are fixed once, here, instead of in every plugin.

Evidence from one consumer (WB Ad Manager Pro 3.2.0): it writes ledger rows
directly (`Ledger::insert`, 3 call sites), reads the ledger table directly
(18 `Ledger::table_name` uses), takes its own `SELECT ... FOR UPDATE` to check
affordability, and keeps a second revenue table so it can tell real money from
hold releases. Every one of those is a primitive the SDK should provide.

## Status

All eight findings are fixed in **1.9.0** and **1.9.1** (see CHANGELOG). The
last part of finding 4, `Consumer` costs with decimals on a money consumer,
was dropped while combining the two 1.9.0 lines and is fixed in **1.9.4**
with the Consumer API unchanged. Finding 5's
`created_at DEFAULT CURRENT_TIMESTAMP` stays: the SDK always writes the column
from PHP, and dropping the default would break a consumer's raw INSERT.

## Findings, most severe first

### 1. `deduct()` without an open hold charges nothing (correctness, money)
`Ledger::deduct_with_hold_release()` (`src/Ledger.php:192`) always writes a
`refund +cost` and a `deduction -cost`. With a hold open, the net effect is the
charge. Without one (the hold was cancelled, never placed, or already settled)
the two rows cancel out: the member is "charged" 0, and a second `deduct()` for
the same item does the same. Nothing links a deduction to the hold it settles.
**Fix:** `settle_hold( $hold_id )` that settles exactly that hold row and
refuses when it is not open; `deduct()` becomes a wrapper that finds the open
hold for the item, or returns false.

### 2. No atomic "spend if affordable" (correctness, money)
`Credits::hold()` (`src/Credits.php:200`) inserts unconditionally. The only
balance check is in `Consumer::on_hold()` (`src/Consumer.php:122`), and it is check-then-insert with no
lock, so two concurrent requests both pass and the balance goes negative.
Consumers each add their own lock (WBAM `FOR UPDATE` in Credits_Bridge; WB
Listora card 10336800031 made `invalidate_cache()` public for this).
**Fix:** `try_hold( $slug, $user_id, $amount, $item_id )` that takes a
per-user lock (`GET_LOCK( "{prefix}_credits_{user}" )`), reads the ledger
uncached, and inserts only when affordable. `hold()` keeps its current
behaviour for callers that allow overdraft.

### 3. Entry types do not say what happened (reporting, forks)
A hold release is written as `refund` ("Hold released on approval",
`src/Ledger.php:199`), while a real gateway refund is written by `adjust()` as
`deduction` (`src/Gateways/Abstract_Gateway.php:255`, WooCommerce adapter
`:371`), and an admin removal is also `deduction`. So `refund` does not mean
money went back, and `deduction` does not mean something was bought. No report
can be built from the ledger alone, which is why consumers keep twin tables.
**Fix:** a `reason` column (`purchase`, `hold`, `hold_release`, `spend`,
`gateway_refund`, `admin_adjust`, `expiry`, …) written by every SDK path,
plus `reference` (gateway session / order id). Keep `entry_type` for sign and
backward compatibility.

### 4. Money mode is opt-in per call site, not enforced (units)
`is_money()` consumers can still call integer `topup()` / `hold()` / `adjust()`
and nothing stops them. The SDK itself branches `is_money ? *_money : raw` in
at least 7 places (Consumer, Abstract_Gateway ×3, AdapterRegistry). `REST.php:210`
admin adjust passes a raw int: minor units in money mode, with no way for the
caller to know that. `low_threshold` defaults to 5 (`src/Credits.php:772`),
which is 5 cents in money mode. `Consumer` costs are `int` major units, so a
money consumer cannot charge 2.50.
**Fix:** one rule: the ledger API always takes ledger units (minor units in
money mode), and major-unit input goes only through `Money`. Have `*_money()`
be the only API documented for money consumers. Make REST adjust money-aware.
Express the threshold in ledger units. Make `Consumer` cost a ledger-unit int.

### 5. Schema never evolves after the first install (upgrades)
`Ledger::maybe_create_table()` returns as soon as the table exists
(`src/Ledger.php:53`), so no column or index change ever reaches an existing
site. `created_at` still has `DEFAULT CURRENT_TIMESTAMP` (server time zone),
and there is no `(user_id, id)` index for history paging. Transaction_Log has
already worked around the same problem with explicit ALTERs.
**Fix:** one versioned migration step per table, keyed on the existing
`wbcom_credits_db_version_{prefix}` option (`src/Registry.php:278`), used for
finding 3's columns and the index.

### 6. `cancel_hold( $item_id )` is still public and unsafe
Its own docblock explains that it can delete an earlier, already-settled hold
and silently reverse that charge (`src/Credits.php:320`, `Ledger.php:230`).
**Fix:** deprecate it (with `_doing_it_wrong`) in favour of
`cancel_hold_by_id()`, and settle holds by id (finding 1).

### 7. Claim and credit are two steps (resilience)
Idempotency claims (`Processed_Events::claim()`) are taken first, and the
top-up happens afterwards, outside any transaction. When the top-up fails
the SDK releases the claim, but a fatal error or timeout between the two keeps the claim and
loses the credit, and the provider's retry is then treated as a duplicate.
**Fix:** write the claim and the ledger row in one transaction (both tables use
the server's default engine, InnoDB on current MySQL/MariaDB), or write the ledger row with a unique `reference` so the row itself
is the claim.

### 8. No read API for reporting, so consumers query tables (forks)
Consumers need per-reason totals and a date range. The SDK offers only a
per-user history and a balance, so WBAM reads the table directly and
converts time zones itself. **Fix:** `Credits::query_ledger( $slug, $args )`
(user, reason, date range in UTC, paging, totals), used by the admin
Transactions screens.

## What is sound and should stay
- Atomic `INSERT IGNORE` claims with a UNIQUE key (Processed_Events).
- One elected copy per request (1.7.0 loader) plus consumer readiness guards.
- `purchase_paths()` / `checkout_enabled()`: the SDK owns "can a member buy?".
- Server-authoritative pricing (1.3.0) and the refund cap at unspent balance (1.8.0).
- The audit script and API-surface snapshot in CI.

## Proposed order
- **1.9.0 (additive, no consumer change needed):** fixes 1, 2, 5 and 6,
  `reason`/`reference` columns written by all SDK paths (3), and REST/threshold
  units (4).
- **1.10.0:** `query_ledger()` (8) and claim+credit in one transaction (7).
  Then each consumer drops its workarounds in its next release: direct
  `Ledger::insert`, own locks, twin tables.
